# แผนรับมือเหตุละเมิดข้อมูลส่วนบุคคล และการหมุนเวียนความลับ (Incident response, 72-hour PDPC notification, secrets rotation) — LENSIQ backend

> **⚠ ต้องผ่านการตรวจทานทางกฎหมาย [ตรวจทานกฎหมาย].** เอกสารนี้เป็นขั้นตอนปฏิบัติงานที่เขียนจากการทำงานจริงของ
> `backend/` (Cloudflare Worker + D1) และหน้าเว็บ ไม่ใช่คำแนะนำทางกฎหมาย ระยะเวลา ช่องทาง และแบบฟอร์มแจ้งเหตุต่อ
> สำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคล (สคส./PDPC) ต้องให้ที่ปรึกษากฎหมายยืนยันตามประกาศ คปช. ที่ใช้บังคับในวันที่เกิดเหตุ
>
> *English: operational runbook for a personal-data breach (PDPA s.37(4): notify the PDPC without delay and, where
> feasible, within 72 hours of becoming aware, unless the breach is unlikely to result in a risk to people's rights and
> freedoms; notify the affected people without delay when the risk is high) and for rotating the Worker's secrets.
> Written from the code; requires legal review.*

## 1. นาฬิกา 72 ชั่วโมง

นับจาก **"เวลาที่รู้"** (เวลาที่ผู้ควบคุมมีเหตุอันควรเชื่อว่าเกิดการละเมิด ไม่ใช่เวลาที่ยืนยันครบทุกอย่าง) [ตรวจทานกฎหมาย]
จดเวลานี้ลงบันทึกเหตุทันที

| ช่วงเวลา | สิ่งที่ต้องทำ |
|---|---|
| 0–1 ชม. | เปิดบันทึกเหตุ (แบบฟอร์มข้อ 6), จำกัดความเสียหาย (ข้อ 2), เก็บหลักฐาน (ข้อ 3) |
| 1–24 ชม. | ประเมินขอบเขตและความเสี่ยง (ข้อ 4); แจ้งผู้ประมวลผลที่เกี่ยวข้อง; ปรึกษาที่ปรึกษากฎหมาย |
| ≤ 72 ชม. | แจ้ง สคส. เว้นแต่ประเมินแล้ว "ไม่มีความเสี่ยง" (บันทึกเหตุผลไว้) — ถ้าข้อมูลยังไม่ครบ ให้แจ้งเท่าที่มีและแจ้งเพิ่มภายหลัง [ตรวจทานกฎหมาย] |
| ทันทีเมื่อความเสี่ยงสูง | แจ้งเจ้าของข้อมูลพร้อมแนวทางเยียวยา (ข้อ 5) |
| ภายใน 30 วัน | ทบทวนหลังเหตุ: สาเหตุ, มาตรการแก้, ปรับ DPIA §14 และ ROPA |

## 2. จำกัดความเสียหาย — ปุ่มที่มีอยู่แล้วในระบบ

| สถานการณ์ | ทำอะไร (ไม่ลบฟีเจอร์ — ปิด/เพิกถอนชั่วคราว) |
|---|---|
| สงสัยว่าบัญชีผู้ดูแลถูกยึด | admin → ความปลอดภัย: เปลี่ยนรหัสผ่าน (ออกจากระบบทุกเครื่อง + ลืมอุปกรณ์ที่เชื่อถือทั้งหมด), `DELETE /admin/api/devices`; ถ้าเข้าไม่ได้: `wrangler d1 execute lensiq --remote --command "DELETE FROM admin_sessions; DELETE FROM admin_devices"` แล้วหมุน `SECRETS_KEK` (ข้อ 7) |
| โทเค็นสมาชิกรั่ว (XSS, อุปกรณ์หาย) | สมาชิก: หน้าบัญชี → "ออกจากระบบทุกอุปกรณ์"; ผู้ดูแล: ระงับบัญชี (`POST /admin/api/members/:id/status {status:"disabled"}` — ลบเซสชันทันที); ทั้งระบบ: `wrangler d1 execute lensiq --remote --command "DELETE FROM member_sessions"` |
| การชำระเงินผิดปกติ | ตั้ง `BILLING_ENABLED = "false"` (checkout ปิด หน้าแสดงสถานะ), `OPN_ALLOW_LIVE = "false"`; ตรวจ admin → Alerts / Payments; หมุนคีย์ Opn (ข้อ 7) |
| AI / ผู้ให้บริการภายนอกรั่ว | ลบ `ANTHROPIC_API_KEY` (`wrangler secret delete`) หรือ admin → AI → ลบคีย์ — หน้าเว็บกลับไปใช้คำทำนายในเครื่อง |
| อีเมลส่งผิด / ผู้ให้บริการอีเมลรั่ว | ตั้ง `MAIL_PROVIDER = ""` (หยุดส่งทันที ทุกฉบับถูกบันทึกเป็น `skipped_not_configured`), หมุน `MAIL_API_KEY` |
| สถิติ / หน้าเว็บถูกแก้ | ตั้ง `ALLOWED_ORIGINS` ให้แคบลง; ตรวจ `GET /admin/api/csp-reports` ว่ามีสคริปต์จากต้นทางแปลกหรือไม่ |
| ทั้ง Worker | `wrangler deployments list` → `wrangler rollback <id>` (กลับรุ่นก่อน) หรือปิด route ชั่วคราว |

## 3. หลักฐาน (เก็บก่อนลบ)

* `GET /admin/api/audit` (200 รายการล่าสุด) และ `wrangler d1 export lensiq --remote --table audit_log --output audit-<date>.sql`
  — เก็บไฟล์ไว้ในที่ปลอดภัย ไม่ commit เข้า repo
* Workers Logs (`[observability]` เปิดอยู่): บรรทัด `alert.*`, `webhook.rejected`, `member.signin.rejected`, `reauth.failed`,
  `cron.failed` — log ไม่มีเนื้อหา อีเมล คีย์ หรือ IP (`util.js log()`)
* `GET /admin/api/alerts`, `GET /admin/api/billing/webhooks`, `GET /admin/api/mail`, `GET /admin/api/csp-reports`
* บันทึกเวลาที่รู้ ผู้ที่รายงาน และสิ่งที่ทำไปแล้วทุกขั้น

## 4. ประเมินขอบเขต — ข้อมูลอะไรอยู่ที่ไหน

| ตาราง D1 | ข้อมูลส่วนบุคคล | ความรุนแรงถ้ารั่ว |
|---|---|---|
| `users` | อีเมล, Google `sub`, ชื่อเล่น, การเลือกรับข่าวสาร/อีเมล | กลาง |
| `payments`, `customers` | ชื่อ/ที่อยู่/เลขผู้เสียภาษีในใบกำกับภาษี, อีเมลผู้ซื้อ, ยอด | กลาง–สูง |
| `saved_readings` | ผลคำทำนายที่สมาชิกบันทึกเอง (อาจสะท้อนความเชื่อ) | กลาง [ตรวจทานกฎหมาย: ม.26 "ความเชื่อในลัทธิ ศาสนา หรือปรัชญา"?] |
| `member_sessions`, `admin_sessions` | แฮช SHA-256 ของโทเค็นเท่านั้น | ต่ำ (ใช้แทนโทเค็นไม่ได้) |
| `admin_users` | แฮช PBKDF2 (100k รอบ — เพดานของ Workers), TOTP เข้ารหัสด้วย `SECRETS_KEK` | สูงถ้า `SECRETS_KEK` รั่วด้วย |
| `webhooks.payload` | payload Opn ดิบ (อาจมีอีเมล) ≤ 90 วัน | กลาง |
| `audit_log`, `events`, `daily_agg`, `csp_reports`, `mail_log` | รหัสสุ่ม/แฮช IP แบบ salt รายวัน/ตัวนับ — ไม่มีอีเมลหรือที่อยู่ | ต่ำ |
| ในเบราว์เซอร์ (ไม่อยู่ใน D1) | descriptor ใบหน้า (customers/attendance, เข้ารหัส AES-GCM), ภาพพื้นหลัง/ภาพของเสียใน QC, แม่แบบใน studio/photobooth | เหตุเกิดที่เครื่องของผู้ควบคุม — ใช้ปุ่มลบในหน้านั้น ๆ |

## 7. การหมุนเวียนความลับ (secrets rotation)

ทำทันทีเมื่อสงสัยว่ารั่ว และตามรอบปกติ (แนะนำทุก 12 เดือน หรือเมื่อคนที่เคยเข้าถึงออกจากทีม) ทุกครั้งบันทึกใน audit/บันทึกเหตุ

| ความลับ | ขั้นตอน | ผลข้างเคียง |
|---|---|---|
| `SECRETS_KEK` (เข้ารหัส TOTP + คีย์ AI ที่ตั้งจาก admin) | 1) ปิด TOTP ใน admin (ต้องใช้รหัสผ่าน + TOTP) และลบคีย์ AI ที่ตั้งจาก admin 2) `openssl rand -base64 32 \| wrangler secret put SECRETS_KEK` 3) ตั้ง TOTP ใหม่ (สแกน QR ใหม่) และตั้งคีย์ AI ใหม่ | ถ้าข้ามข้อ 1 TOTP/คีย์เดิมจะถอดรหัสไม่ได้ — เจ้าของเข้าด้วยรหัสผ่านอย่างเดียวไม่ได้ขณะที่ billing เปิด: ใช้ `wrangler d1 execute … "UPDATE admin_users SET totp_enabled = 0, totp_secret_enc = NULL WHERE id = 1"` แล้วตั้ง TOTP ใหม่ทันที |
| `TURNSTILE_SECRET` | Cloudflare dashboard → Turnstile → Rotate secret → `wrangler secret put TURNSTILE_SECRET` | ช่วงไม่กี่วินาทีที่คีย์ไม่ตรง การเข้าสู่ระบบ/checkout/AI จะถูกปฏิเสธ (fail closed) แล้วกลับมาเอง |
| `OPN_SECRET_KEY`, `OPN_PUBLIC_KEY` | Opn dashboard → Keys → สร้างคีย์ใหม่ → `wrangler secret put` ทั้งสอง → ทดสอบ test charge (admin, ต้อง re-auth) → ยกเลิกคีย์เก่าใน Opn | QR ที่ออกไปแล้วยังจ่ายได้ (charge อยู่ที่ Opn); poll/cron ใช้คีย์ใหม่ |
| `OPN_WEBHOOK_SECRET` | Opn dashboard → Webhooks → สร้าง secret ใหม่ → `wrangler secret put OPN_WEBHOOK_SECRET` | webhook ที่มาระหว่างเปลี่ยนจะถูกปฏิเสธ 401 — cron reconcile/sweep ทุก 15 นาทีเก็บตกให้เอง |
| `MAIL_API_KEY` | ผู้ให้บริการอีเมล → สร้างคีย์ใหม่ → `wrangler secret put MAIL_API_KEY` → ยกเลิกคีย์เก่า | อีเมลที่ล้มเหลวระหว่างนั้นบันทึกเป็น `failed` ใน `mail_log` (ไม่ส่งซ้ำอัตโนมัติ; เอกสารยังอยู่ในหน้าบัญชี) |
| `ANTHROPIC_API_KEY` | Anthropic Console → สร้างคีย์ใหม่ → `wrangler secret put` → ยกเลิกคีย์เก่า | ระหว่างนั้นหน้าเว็บใช้คำทำนายในเครื่อง |
| `ALERT_WEBHOOK_URL`, `HEALTH_TOKEN` | สร้าง URL/โทเค็นใหม่ → `wrangler secret put` | — |
| `ADMIN_BOOTSTRAP_TOKEN` | ควรถูกลบแล้วหลังสร้างบัญชีเจ้าของ: `wrangler secret delete ADMIN_BOOTSTRAP_TOKEN` | bootstrap ทำได้ครั้งเดียวอยู่แล้ว |
| รหัสผ่านเจ้าของ | admin → เปลี่ยนรหัสผ่าน (ออกจากระบบทุกเครื่อง, ลืมอุปกรณ์ทั้งหมด) | — |

## 8. ซ้อมแผน (drill)

* ซ้อมอย่างน้อยปีละครั้งบน **staging** (Worker + D1 แยกจากของจริง, คีย์ Opn TEST): จำลอง "โทเค็นสมาชิกรั่ว" → ออกจากระบบทุกอุปกรณ์ +
  ระงับบัญชี; จำลอง "คีย์ Opn รั่ว" → หมุนคีย์ตามข้อ 7; จับเวลาจนถึงร่างข้อความแจ้ง สคส. (เป้าหมาย < 24 ชม.)
* บันทึกผลซ้อมในบันทึกเหตุ (ข้อ 6) ระบุว่าเป็นการซ้อม
* **ยังไม่ได้ซ้อม** — ต้องมี staging account (Cloudflare) และผู้รับผิดชอบตามข้อ 0 ก่อน
